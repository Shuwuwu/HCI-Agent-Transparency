# CS889 HCI Agent Transparency Project

A user study on whether showing a workspace agent's action log helps people notice unauthorized behaviour. The
stimuli come from recorded `gpt-4o-2024-05-13` runs of AgentDojo's **workspace** suite (email, calendar, cloud
drive), pinned to AgentDojo commit `af7266303c748a9cf0442d71ceabc9d2488d7188`. Participants judge whether the
agent's behaviour matches the user's request, with or without the execution trace, and can read the SKILL.md
documents the agent is said to have followed.

## Scripts

Scenario selection and AgentDojo access:

| Script | What it does |
|---|---|
| `agentdojo_runs.py` | Shared parsing of recorded runs and the constants that describe them (tool groups, write tools, injection goals). |
| `agentdojo_source.py` | Read-only access to AgentDojo's source files and traces at the pinned commit; writes the source manifest. |
| `agentdojo_tools.py` | The 24 workspace tools as the agent saw them (descriptions and argument schemas), derived from AgentDojo's source. |
| `extract_scenarios.py` | Builds `gpt4o_workspace_scenarios.json` from the recorded runs. |
| `injection_design.py` | The unsafe-stimulus design as data and pure functions: objectives G1-G4 (AgentDojo injection tasks 1-4), AgentDojo's two strategies (`important_instructions` = II, `tool_knowledge` = TK), wordings W1 (AgentDojo template verbatim), W2 (our adaptation) and W3 (our contextual adaptation: prose inside an existing workflow, three variants). The study plan uses strategy II only, with all three wordings mixed over the 12 items (four each; `STUDY_STRATEGIES`, `STUDY_WORDINGS`), objectives and attacker identities kept from the earlier II + W2 allocation (`OBJECTIVE_BASIS`, `allocate_study_items`); TK is implemented but unused. Also: the attacker-identity pool, placement in a skill, and the allocation of items to candidate scenarios. Needs no AgentDojo. |
| `injection_checks.py` | Judges an injected run with AgentDojo's own checks: the parametrised security check (item's attacker identity), the attack-tolerant utility check (the legitimate task alone, after removing the injected calls) and the inclusion verdict. Run it with `.venv-agentdojo/bin/python`. |
| `select_scenarios.py` | The scenario-selection pipeline (rules R1-R7; R7 replaces a candidate whose safe stimulus the study corpus excludes after manual review by the first spare that keeps a valid final set, without changing stage 1): writes `src/data/scenario_selection.csv` and `docs/scenario_selection.md` (from `docs/scenario_selection.template.md`); `--collect` refreshes the facts with AgentDojo; `--check` fails if the generated files are stale. Stage 2 takes the passing unsafe items from the simulated stimuli: an item passes when its simulated record passed the inclusion checks and its stimulus is marked `reviewed` in `src/data/simulated/review.json` (which must be current); it fills the CSV columns `simulated_included`, `review_status`, `stage2_status` and picks the final 8. The real injected runs (`injected_evaluation.json`) are not a stage-2 input. |
| `build_injected_items.py` | Builds the 12 injected skill items and the manifest, and the R7 replacement items (`replacements/`), from the selection pipeline; verifies each against the skill the safe run used. `--wordings W1,W2 --out-dir <scratch>` rebuilds the first two-wording plan without touching the committed corpus. |
| `build_injection_plan.py` | Builds `plan_injected_v1.json` (spends nothing) and, with `--next-round`, lists the run ids still needed (at most 3 attempts per item). `run_executions.py` runs injected specs (security result recorded). |
| `generate_injected_text.py` | Experimental, SkillJect-inspired text generation for one candidate item at a time (`--scenario --objective [--identity] [--attempts]`); `--dry-run` picks the anchor and prints it, sending nothing. Candidates are validated automatically (pure insertion, length bounds, required facts present, no banned/template phrasing) and written to `src/data/injected_skills/generated/`, status `pending_review`. Not wired into the study pipeline; its output is supplementary material only (see `src/data/injected_skills/generated/` above). |
| `corpus.py` | Loads a corpus configuration and decides, from the execution record behind a stimulus, whether a rule accepts it (safe runs, included injected runs, simulated fixtures). No identifier naming convention is assumed except the pattern the corpus file gives. |
| `build_simulated_stimulus.py` | Builds the one simulated unsafe stimulus under `src/data/validation/` offline (no model, no key): the safe run of an injected item plus AgentDojo's own correct-solution attack calls, replayed through AgentDojo's tools. Run it with `.venv-agentdojo/bin/python`. Its record builder is shared with `build_simulated_items.py`. |
| `build_simulated_items.py` | Builds the simulated unsafe stimuli of the 12 planned items and any R7 replacement into `src/data/simulated/` with the same method (no model, no key, no attack against a model); labels each record `material_kind: simulated_trace`, cites the matching recordings of `reference_recordings.json`, and writes `manifest.json`. `--items` builds a subset; `--check` fails if a record is stale. Run it with `.venv-agentdojo/bin/python`. |
| `review_stimuli.py` | Stimulus review: 10 automated checks (completeness, low/high parity, fidelity to the execution record, before-state workspace, skills, no researcher-only identifiers served, and provenance: the record matches its hash and, for a simulated record, its safe run, skills, attack calls and inclusion verdict) and a 7-item manual checklist; `--write`, `--check`, `--mark`. Statuses: unreviewed, reviewed, rejected, stale, auto_failed. |

## Skill pipeline: status

The skills are a small library of reusable **capability skills** (calendar lookup, calendar scheduling, email lookup,
email correspondence, drive file management, document content), not one skill per scenario. Each skill covers one
workflow family, a scenario may use several, and each of the 10 data-changing tools belongs to exactly one skill. The
categories come from Yang et al. 2025 (arXiv 2512.07828, Table 1, topic Productivity & Workflow). The first pilot
generated one skill per scenario and was found to produce task-shaped skills that leak scenario content; see
`archive/2026-11-14_per_scenario_pilot/README.md`.

Done: taxonomy, scenario map and checker; scenario stimuli folders with `skills.json`; per-skill source packages and
generation prompts; the per-skill static validator; the generator. The prompts are task-agnostic: the generator is shown a skill's scope, workflows, tool
specifications and record schemas, and no scenario, example request, trace or answer.

All six skills are generated and pass the validator (`capability_validator_v5`, generated with prompt `skill_capability_v4`). An experimental prompt `skill_capability_v5` (general guidance for dates without a year, searching again after an empty search, and answer formats, derived from the recurring `skills-v4b` failures) exists beside v4 in `src/data/skill_library/experimental/prompt_v5/`; **no skill has been generated or run with it** (see its `README.md`). The review sheet is built and waiting for the two raters. The execution pipeline is built and has run once as a pilot (one scenario, two runs; see `src/data/execution/summary.json`); the pilot records and `plan.json` refer to the previous skills (prompt v3), recoverable from the attempt logs. The mapped-skills batch `skills-v4b` (25 scenarios, `gpt-4o-2024-08-06`, one run each, current skills) has been executed; its stimuli are built and its traces exported to `src/data/explorer/mapped_skills_v4b/`. The trace-to-stimulus pipeline is built and tested; the 20 successful runs of the batch are the active stimuli (the stimuli of the 5 failed runs, the pilot runs and a recorded attacked run were archived; their run records stay in `src/data/execution/runs/`; see `archive/README.md`). The unsafe-stimulus design is prepared (scenario selection, 12 injected skill items, the injected-run plan, assignments). The first injected run of each of the 12 items was executed and none carried out the injected action, so the unsafe stimuli of the 12 study items are built as **simulated** (constructed) traces in `src/data/simulated/` (all 12 pass the inclusion checks and the automated review checks; no manual review yet; the study corpus serves an item only once it is marked reviewed, and stage 2 picks the final 8 only from reviewed items; the methods and limitations are in `docs/scenario_selection.md`). For interface validation there is one simulated unsafe stimulus (`src/data/validation/`, built offline, separate corpus); the 20 study stimuli and the fixture pass the automated review checks, and **no manual review has been recorded yet**. Not done yet: the manual review of the 12 simulated unsafe stimuli (and of the 20 safe ones), then the study assignments (`build_assignments.py --write`).
