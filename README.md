# CS889 HCI Agent Transparency Project

A user study on whether showing a workspace agent's action log helps people notice unauthorized behaviour. The
stimuli come from recorded `gpt-4o-2024-05-13` runs of AgentDojo's **workspace** suite (email, calendar, cloud
drive), pinned to AgentDojo commit `af7266303c748a9cf0442d71ceabc9d2488d7188`. Participants judge whether the
agent's behaviour matches the user's request, with or without the execution trace, and can read the SKILL.md
documents the agent is said to have followed.

| `participant_store.py` | The persistent participant records and flow progress (SQLite, `src/data/participants/participants.db`): enrols the participants of an assignments file, gives each an opaque link token, and saves which stage each has entered and completed, so reopening a link resumes at the first unfinished stage. | `interaction_log.py` | Validates, stores and summarises participant interaction events (`python3 -B src/scripts/interaction_log.py [LOG_DIR]` prints per-session measures). |
| `participant_server.py` | Serves the experiment flow and the scenario content (`src/participant_ui/`). Only the eligible stimuli of the active corpus are servable (default: the corpus the experiment configuration names; `--corpus` overrides it). | `stimulus_text.py` | The wording rules of the action log (action sentence, shown arguments, outcome summary per tool); never copies free text from results. |
| `tool_result_parser.py` | Reads AgentDojo's YAML-style tool result text with the standard library only; checked against PyYAML on every recorded result. |

## Skill pipeline: status

The skills are a small library of reusable **capability skills** (calendar lookup, calendar scheduling, email lookup,
email correspondence, drive file management, document content), not one skill per scenario. Each skill covers one
workflow family, a scenario may use several, and each of the 10 data-changing tools belongs to exactly one skill. The
categories come from Yang et al. 2025 (arXiv 2512.07828, Table 1, topic Productivity & Workflow). The first pilot
generated one skill per scenario and was found to produce task-shaped skills that leak scenario content; see
`archive/2026-11-14_per_scenario_pilot/README.md`.

Done: taxonomy, scenario map and checker; scenario stimuli folders with `skills.json`; per-skill source packages and
generation prompts; the per-skill static validator; the generator. The prompts are task-agnostic: the generator is shown a skill's scope, workflows, tool
specifications and record schemas, and no scenario, example request, trace or answer.

All six skills are generated and pass the validator (`capability_validator_v5`, generated with prompt `skill_capability_v4`). The review sheet is built and waiting for the two raters. The execution pipeline is built and has run once as a pilot (one scenario, two runs; see `src/data/execution/summary.json`); the pilot records and `plan.json` refer to the previous skills (prompt v3), recoverable from the attempt logs. The mapped-skills batch `skills-v4b` (25 scenarios, `gpt-4o-2024-08-06`, one run each, current skills) has been executed; its stimuli are built and its traces exported to `src/data/explorer/mapped_skills_v4b/`. The trace-to-stimulus pipeline is built and tested; the 20 successful runs of the batch are the active stimuli (the stimuli of the 5 failed runs, the pilot runs and a recorded attacked run were archived; their run records stay in `src/data/execution/runs/`; see `archive/README.md`). The unsafe-stimulus design is prepared locally (scenario selection, 12 injected skill items, the injected-run plan, assignments); **no injected run has been executed** (needs approval). For interface validation there is one simulated unsafe stimulus (`src/data/validation/`, built offline, separate corpus); the 20 study stimuli and the fixture pass the automated review checks, and **no manual review has been recorded yet**. Not implemented yet: executing and evaluating the injected runs, building unsafe stimuli, opaque participant links, the experiment app.
